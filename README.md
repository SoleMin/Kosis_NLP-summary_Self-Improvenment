# kosis_loop

Phase 1의 숫자 계산을 개선하는 루프. 평가자, 공격자, 방어자 세 에이전트를 `scripts/loop.sh`가 차례로 실행한다.
한 루프에서 공격자가 약점을 찌르는 문항을 만들고, 방어자가 코드를 고치고, 점수가 조건을 만족하면 커밋하고 아니면 되돌린다.

## 시작하기

1. `loop/config.env`에 설정을 넣는다. 넣을 항목은 `loop/config.example.env`에 있다 (에이전트 명령, 표가 있는 폴더, 루프 수).
2. Phase 1 클론(`kosis-ai-nlp-summary-T1-30/`)이 루프 전용 브랜치에 있고 커밋하지 않은 변경이 없는지 확인한다.
3. 설정을 점검한다. 루프가 쓰는 파이썬의 pyarrow가 15 이상인지도 여기서 확인한다 (Phase 1의 요구 사항. 낮은 버전에서는 표 보기 도구가 일부 표를 읽지 못한다).
   파이썬은 conda 환경 `kosis`의 것을 쓴다. `scripts/loop.sh`가 그 환경의 폴더를 찾아 PATH 맨 앞에 두므로 환경을 켜지 않은 셸에서 실행해도 되고, 세 에이전트가 실행하는 `python`도 같은 것이 된다. 실행하면 첫 줄에 쓰는 파이썬의 경로가 나온다. 환경을 찾지 못하면 `loop/config.env`의 `CONDA_ENV_DIR`에 폴더를 적는다 (`scripts/use_python.sh`).
   ```bash
   bash scripts/loop.sh --check
   ```
4. 한 루프만 돌려 본다. 문제가 없으면 옵션 없이 실행한다. 중간에 멈추려면 `loop/STOP` 파일을 만든다.
   ```bash
   bash scripts/loop.sh --once
   bash scripts/loop.sh
   ```

실행이 중간에 끊겨 `evals/` 폴더가 보이지 않으면 `bash scripts/loop.sh --restore`로 되돌린다.

## 한 루프의 순서

| 순서 | 누가 | 하는 일 | 결과 파일 |
|---|---|---|---|
| 0 | 스크립트 | 기준 데이터(판정용) 점수 측정. 측정은 모두 규칙만으로 함(모델 호출 없음, `EVAL_BACKEND=rules`). 클론의 커밋, 설정, 채점 코드(`evals/*.py`), 기준 문항과 분할 파일이 모두 같을 때만 저장된 점수를 다시 씀 | `evals/runs/loop-N/dev-before/` |
| 1 | 평가자 | 공격 힌트 | `loop/attack/hint_N.md` |
| 2 | 공격자 | 공격 문항 (질문, 칸 좌표, 계산식). 목표 건수를 못 채우면 탐색 보고 | `loop/attack/spec_N.jsonl`, `spec_N.search.md` |
| 2' | 평가자 | 공격 문항이 `ATTACK_MIN`건 미만일 때만: 탐색 보고 심사. 받아들이면 최종 verify 뒤 목표 완료, 아니면 심사 탈락 또는 운영 오류 | `loop/attack/search_N.json` |
| 3 | 평가자 | 1차 판정. 판정이 빠진 문항은 다시 요청. 절반 이상 부적절이면 한 번 다시 작성 | `loop/attack/judge1_N.jsonl` |
| 4 | 스크립트 | 표에서 값 채우기와 검증 | `evals/golden_N.jsonl` |
| 5 | 평가자 | 2차 판정. 탈락 문항 제외. 5건 미만이 남으면 공격 세트로 등록하지 않고 끝냄 | `loop/attack/judge2_N.jsonl` |
| 6 | 스크립트 | 수정 전 점수 (이번 공격, 지난 공격) | `evals/runs/loop-N/` |
| 7 | 평가자 | 방어자용 약점 설명. 스크립트가 문항 유출을 검사하고 집계를 붙임 | `loop/defender/brief_N.md` |
| 8 | 방어자 | 코드 수정. 그동안 `evals/`, `loop/attack/`, `loop/runs/`는 보관 폴더로 옮김 | 클론, `loop/defender/notes_N.md` |
| 9 | 스크립트 | 허용 범위, 공용 형식 파일 검사, 접근 흔적, verify, 방어자의 테스트를 수정 전 코드와 수정 후 코드에서 돌려 보기(수정 전에 실패하고 수정 후에 통과하는 것이 있어야 함), 수정 후 점수, 유지 조건 | `loop/runs/loop-N/outcome.md` |
| 10 | 평가자 | 수정 판정(받아들일 때는 고친 원인, 검증 테스트, 남은 실패를 함께 적음)과 기록. 기록은 초안에 쓰고 스크립트가 문항 유출을 검사한 뒤 공개. 수정이 없는 루프도 기록 | `loop/critic/code_N.json`, 초안 `loop/attack/records_N/` → `loop/log.md`, `loop/learnings.md`, `docs/current-state.md` |
| 11 | 스크립트 | 클론에서 커밋 또는 되돌림, 점수표 한 줄 | `loop/results.tsv` |

유지 조건: 기준 데이터와 지난 공격 문항은 점수와 칸 일치 점수가 모두 떨어지지 않음(지난 공격은 합친 점수와 세트 하나하나 모두), 이번 공격 문항은 칸 일치 점수가 오르고 점수가 떨어지지 않음, 방어자의 테스트 가운데 수정 전 코드에서 실패하고 수정 후 코드에서 통과하는 것이 있고 수정 후에 실패하는 것이 없음, 평가자가 수정을 받아들임. 테스트는 `tests/loop/`의 하위 폴더까지 같은 파일을 수정 전후에 돌려 테스트마다 견준다. `outcome.md`에는 기준 데이터와 지난 공격 문항에서 점수가 떨어진 문항과 오른 문항의 건수를 적는다. 건수는 기록일 뿐 유지 판정에 쓰지 않는다.

칸 일치 점수는 계산 값이 정답과 같은 칸들에서 계산된 경우에만 인정하는 점수다 (`evals/grade.py`의 `score_same_inputs`). 값만 우연히 같은 답은 점수는 받지만 칸 일치 점수는 받지 못한다. `loop/results.tsv`의 뒤쪽 여섯 칸(`dev_strict_before` 등)에 적힌다.

## 루프가 멈추는 조건

멈춘 이유는 마지막 줄 `종료: ...`와 기록에서 구별된다.

| 구분 | 언제 | 기록 | 다시 실행하면 |
|---|---|---|---|
| 목표 완료 | 공격자가 정상적으로 끝내고 탐색 보고와 함께 `ATTACK_MIN`건 미만을 냈고, 평가자가 그 보고를 받아들였고, 최종 verify를 통과함 | `loop/results.tsv`에 `kept=done` | 다음 루프 번호 |
| 심사 탈락 | 다시 쓴 공격 문항도 절반 이상 부적절, 또는 판정·값 채우기를 통과한 문항이 `ATTACK_MIN`건 미만. 공격자의 탐색이 모자란 경우(이유가 "탐색 부족"으로 시작), 약점 부족으로 끝났는데 최종 verify가 실패한 경우도 여기 | `kept=stop` | 다음 루프 번호 |
| 사람에게 넘김 | `loop/blocked.md`에 내용이 생김 (에이전트가 쓰거나, 평가자의 기록에 문항 내용이 섞여 스크립트가 씀) | `kept=blocked` (기록 유출은 그 루프의 결과 줄 그대로) | 파일을 비울 때까지 시작하지 않음 |
| 운영 오류 | 에이전트가 실패하거나 시간 초과로 끝나 결과 파일이 없음, 결과 파일 형식이 깨짐(문항 파일의 깨진 줄, 채워지지 않는 판정), 측정 실패(표를 읽지 못한 문항이 있음, 기준 데이터의 절반 이상이 오류), 값 채우기 스크립트가 보고서 없이 실패, 공격자의 탐색 도구가 동작하지 않음(`tools`), 보호 파일 변경, 방어자용 설명의 문항 유출, 실행기 오류 | `loop/results.tsv`에 줄 없음. `loop/faults.tsv`에 한 줄 (시각, 루프, 종류, 이유). 종료 코드 1 | 같은 루프 번호부터 다시 |
| 한도 | `MAX_ITER` 도달, `PATIENCE`번 연속으로 수정을 유지하지 못함, `loop/STOP` 파일 | | 다음 루프 번호 |

- 규칙만으로 잴 때 코드가 오류로 끝난 문항은 0점으로 세고 계속한다. 운영 오류가 아니다. 표를 읽지 못한 문항은 다르다. 코드의 결과가 아니므로 0점으로 세지 않고, 한 번 다시 돌려도 남으면 운영 오류(`measure`)로 멈춘다.
- 공격 문항이 `ATTACK_MIN`건 미만이어도 공격자의 실행이 끊겼거나 탐색 보고가 없으면 목표 완료로 보지 않는다. 운영 오류다.
- 운영 오류나 사람에게 넘김으로 끝날 때 클론에 방어자의 수정이 남아 있으면 `loop/runs/loop-N/unfinished.diff`(넘긴 경우 `blocked.diff`)에 저장하고 클론을 되돌린다. 커밋하지 않는다. `git apply`로 다시 적용해 볼 수 있다. 저장에 실패하면(git 오류, 저장한 내용이 수정과 맞지 않음) 클론을 되돌리지 않고 수정을 그대로 둔다. 종료 줄에 그렇게 적히고, 사람이 확인해 정리할 때까지 `--check`가 통과하지 않는다.
- 시작할 때 기록 파일(`loop/log.md`, `loop/learnings.md`, `docs/current-state.md`)이 마지막 검사 뒤에 바뀌었으면 문항 내용이 섞였는지 다시 검사한다. 섞여 있으면 고칠 때까지 시작하지 않는다.
- 에이전트의 실패(사용량 한도, 연결 끊김)는 먼저 기다렸다가 다시 실행한다. 아래 "에이전트가 실패했을 때"

## 평가자의 기록에 문항 내용이 섞였을 때

평가자는 기록을 초안(`loop/attack/records_N/`)에 쓴다. 스크립트는 초안에서 이번에 더해진 줄을 이번 공격 문항과 지난 공격 문항에 견주어 검사하고, 깨끗할 때만 `loop/log.md`, `loop/learnings.md`, `docs/current-state.md`로 옮긴다. 섞였으면 평가자에게 한 번 다시 쓰게 한다. 그래도 남으면

- 기록을 공개하지 않는다. 초안은 방어자가 볼 수 없는 `loop/attack/records_N/`에 그대로 둔다.
- `loop/blocked.md`에 걸린 파일과 문항 id, 할 일을 적는다. 그 루프의 결과(유지 또는 되돌림)는 그대로 기록하고 루프를 멈춘다.
- 사람이 초안에서 문항 내용을 지우고 세 파일에 옮긴 뒤 `loop/blocked.md`를 비우면 다시 시작한다. 옮긴 파일은 시작할 때 다시 검사된다.

## 에이전트가 실패했을 때

에이전트가 자기 단계의 결과 파일을 쓰지 못한 채 실패 종료 코드로 끝나거나, 로그 끝에 한도 문구(usage limit, rate limit 등)가 있으면 그 단계는 실패로 본다. 방어자는 종료 코드가 실패이면 코드를 일부 고쳤더라도 실패로 보고, 클론을 되돌린 뒤 다시 실행한다.

- 실패한 단계는 `AGENT_RETRY_WAIT`초(30분) 뒤에 다시 실행한다. 최대 `AGENT_RETRY_MAX`번(12번, 6시간)까지 한다.
- 다시 실행한 것이 10분 넘게 일한 뒤 또 실패하면 더 기다리지 않는다.
- 30초 안에 한도 문구 없이 끝난 실패는 설정 문제(명령, 실행 파일, 모델 이름)일 수 있어 60초 뒤 다시 하고, 3번 이어지면 운영 오류 `agent`로 멈춘다. 다만 같은 단계의 앞선 시도에 한도 문구가 있었으면 한도가 아직 안 풀린 것으로 보고 30분씩 기다리는 보통 재시도로 센다.
- 끝내 안 되면 그 루프를 `loop/results.tsv`에 기록하지 않고 멈춘다. 연속 실패 횟수에도 세지 않는다. 다시 실행하면 같은 루프 번호부터 처음부터 한다(기준 점수는 다시 재지 않고 저장된 것을 씀).
- 기다리는 중에 `loop/STOP` 파일을 만들면 바로 멈춘다.
- `AGENT_TIMEOUT`으로 끊긴 실행은 다시 실행하지 않는다. 그 단계의 결과 파일이 있으면 그대로 진행하고, 없으면 운영 오류로 멈춘다.

## 한계

- 보관용 문항은 문서의 금지 문구로만 지킨다. 기준 문항 파일(`evals/baseline/items.jsonl`)에 판정용과 함께 들어 있어, 평가자와 공격자가 읽는 것을 막는 장치는 아직 없다.
- 공격 문항의 배분(다중 표 비율, 한 유형·한 표의 비율)은 지침이며 스크립트가 검사하지 않는다.
- 질문이 자연스러운지(`docs/ATTACKER.md`의 "자연스러운 질문의 기준")와 방어자의 조건이 표현 하나에 맞춘 것인지(`docs/DEFENDER.md`의 "조건을 넣는 기준")는 평가자가 판정한다. 스크립트가 검사하지 않는다. 스크립트가 받치는 것은 방어자가 문항을 볼 수 없다는 것, 기준 데이터와 지난 공격의 점수가 떨어지면 되돌린다는 것, 수정 전 코드에서 실패하는 테스트가 있어야 한다는 것이다.
- "더 찾을 약점이 없음"은 평가자가 공격자의 탐색 보고를 실행 기록과 견주어 심사한다. 스크립트는 질문을 돌려 본 횟수만 센다. 심사도 에이전트의 판단이므로, 목표 완료로 끝난 뒤 사람이 `loop/attack/spec_N.search.md`와 `loop/attack/search_N.json`을 읽어 확인한다.
- 방어자의 테스트는 수정 전 코드와 수정 후 코드 모두 빈 작업 폴더(`KOSIS_WORKSPACE`)에서 돌린다. 표 색인 코드(`kosis_chat/shared/`, `kosis_chat/prepare/index.py`)가 바뀐 수정도 수정 전 코드에서 돌리고, 실제 표의 저장된 색인은 건드리지 않는다. 루프 1~4는 방어자가 매번 `kosis_chat/shared/patterns.py`를 고쳐 이 검사를 건너뛰었고, 평가자의 `before_fix`가 대신했다 (`loop/critic/code_1~4.json`, 사람이 확인할 것).
- 칸 일치 점수는 정답의 계산식이 쓴 칸과 같은 칸에서 계산했는지만 본다. 같은 칸으로 다른 계산을 했는데 값이 우연히 같은 답(2와 2의 합과 곱)은 채점으로 가리지 못한다. 그래서 공격 문항을 만들 때 걸러 낸다. 계산식의 `+ - * /` 하나를 다른 것으로 바꾸거나 빼기·나누기의 두 쪽을 바꿔도 답이 같은 명세는 `build_items.py`가 탈락시킨다. 기준 데이터 600건에는 그런 문항이 3건 있고 그대로 둔다. 연산 기호 둘 이상이 함께 바뀐 경우와, 표의 값 자체를 바꾼 변형 문항은 다루지 않는다.
- 다중 표 규칙(`kosis_chat/analyze/multi_rules.py`)은 루프가 재는 계산 입구(`kosis_chat/calc.py`)에서만 쓰인다. 같은 클론의 공개 함수(`kosis_chat/api.py`의 `summarize_stats_run`)는 다중 표 질문에서 모델이 쓴 계획(`step_plan_multi_llm`)을 쓴다. 루프가 다중 표 규칙을 고쳐 점수가 올라도 챗봇의 답이 달라지는 것은 아니다. 챗봇 경로에 연결할지는 정해야 할 것으로 남아 있다.
- 수정이 목표로 한 실패 유형의 점수가 올랐는지는 스크립트가 따로 재지 않는다. 평가자가 판정의 `cause`와 `remaining`에 적는 내용과 방어자의 테스트로 확인한다.
- 기록의 문항 유출 검사는 이번에 더해진 줄만 본다. 질문 문구의 일부, 표 번호, 큰 정답 값을 찾는 방식이라 돌려 쓴 표현은 잡지 못한다.
- `protect.js`는 Claude Code에서만 동작한다. Codex로 도는 역할은 실행 뒤 스크립트의 검사(보호 파일 해시, 클론 변경)로만 막는다.
- Bash 명령 검사는 명령 문자열만 보고 판단해서 우회가 가능하다. 방어자의 읽기는 폴더를 옮기는 것으로 막는다.
- 방어자의 접근 흔적 검사는 Claude Code의 stream-json 로그에서만 된다.
- 비용 한도는 `MAX_ITER`와 에이전트 명령의 `--max-turns`, `AGENT_TIMEOUT`으로만 제한한다.
- `CRITIC_LIGHT_CMD`를 정하면 평가자의 가벼운 단계(1 힌트, 3·5 판정과 다시 요청, 7 브리프 다시 쓰기, 10 기록 초안과 기록 다시 쓰기)는 그 명령으로 돈다. 탐색 심사(2'), 브리프(7 첫 작성), 코드 검토(10)는 늘 `CRITIC_CMD`. 어느 명령으로 돌았는지는 `state.json`의 시작 줄에 `light=1`로 남는다.
