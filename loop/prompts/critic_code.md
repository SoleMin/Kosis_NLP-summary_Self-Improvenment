   - 고친 원인을 확인한다. 약점 설명이 짚은 실패 원인 가운데 이번 수정이 어느 것을 고쳤는지 diff에서 확인하고 `cause`에 적는다(어느 단계의 무엇이 잘못되어 어떤 질문이 틀렸는지). 점수는 올랐는데 약점 설명의 원인과 관계없는 수정이면 거부한다.
   - 이번 수정을 검증하는 테스트를 본다. 방어자가 추가한 테스트(`tests/loop/`)가 수정 전 코드에서 실패하고 수정 후 통과해야 한다(`outcome.md`의 "방어자의 테스트"). 추가한 테스트가 없거나 수정 전에도 통과하면 스크립트가 이미 되돌린다. 테스트가 고친 동작을 실제로 확인하는지, 한 가지 질문만이 아니라 같은 동작을 다른 표현·다른 기간이나 지역·다른 표로 묻는 질문까지 확인하는지 본다. 고친 동작과 관계없는 것만 확인하는 테스트이거나 질문 하나에만 맞춘 테스트이면 거부한다. `outcome.md`에 "수정 전 코드로는 돌려 보지 않음"이라고 적혀 있으면(표 색인 코드가 바뀐 수정) 스크립트의 확인을 네가 대신한다. 테스트와 수정 전 코드를 읽고 그 테스트가 수정 전 코드에서 실패하는 이유를 `before_fix`에 적는다(어느 입력에서 수정 전 코드가 무엇을 돌려주어 어느 확인이 실패하는지). 이유를 댈 수 없으면 거부한다. 그 밖의 경우에는 `before_fix`를 쓰지 않아도 된다.
   - `tests`에는 어느 테스트가 이번 수정의 어떤 동작을 어떤 변형 질문으로 확인하는지 적는다.
   - `remaining`에는 이번 공격에서 수정 후에도 틀리는 유형과 이유를 적는다(`evals/runs/loop-{{LOOP_NUM}}/attack-after/`의 집계). 없으면 "없음"이라고 적는다.

```
{"verdict": "accept", "reason": "한두 문장", "cause": "고친 실패 원인: 어느 단계의 무엇", "tests": "어느 테스트가 어떤 동작을 어떤 변형 질문으로 확인하는지", "remaining": "수정 후에도 틀리는 유형과 이유, 없으면 없음"}
```

   `verdict`는 `accept` 또는 `reject`다. `accept`이면 `reason`, `cause`, `tests`, `remaining`을 모두 채운다(위의 경우에는 `before_fix`도). 비어 있으면 다시 요청받는다. 기록에 문항 내용이 섞여 이 파일을 다시 쓰게 되면 같은 판정과 같은 항목을 모두 다시 적는다. 다시 쓴 파일의 판정이 달라졌거나 항목이 비면 수정은 커밋되지 않는다. `reject`이면 `reason`을 채운다. 스크립트 판정이 이미 "되돌림"이어도 판정과 이유를 쓴다. 이 파일은 다음 루프의 방어자도 읽을 수 있으므로 어느 항목에도 질문 문구, 표 이름, 분류 이름, 정답 값은 적지 않는다.
